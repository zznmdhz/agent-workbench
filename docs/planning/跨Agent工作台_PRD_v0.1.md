# 跨 Agent 工作台：产品需求与技术设计（PRD v0.1）

版本日期：2026-09-23  |  状态：开发验证初稿

覆盖：Windows + Mac / Codex + Hermes / NAS Web 汇总 / 可选跨设备接续

> 本文基于用户两轮需求与官方资料核查。未访问用户电脑或 NAS，尚未完成实机兼容性、性能及数据覆盖验证。资源指标为设计预算。

## 01  产品决策与阅读导航

把需求落成可验证的产品方案，而不是直接承诺所有数据都能完整还原。

> 推荐形态：NAS 上一个 Web 汇总服务 + Windows、Mac 各一个轻量采集器。双机汇总进入首个可用版本；跨设备继续工作分层实现，不阻塞核心统计。

| 事项 | 本版决策 |
| --- | --- |
| 数据中心 | NAS 统一保存本工具的记录、索引、配置和交接快照；两台电脑通过 API 上传，不共写数据库文件。 |
| 客户端 | 浏览器负责查看；后台采集器负责读取本机 Agent 记录、断网缓存和上报。首版不做完整桌面壳。 |
| 已有工具 | 继续使用现有 Codex、Hermes，不强制更换调用入口、模型供应商或登录方式。 |
| 跨设备接续 | 先保证记录和文件清单可回看，再提供一键交接上下文；官方原生续聊能力另行接入。 |
| NAS 负载 | 仅运行数据服务与搜索，不在 NAS 部署大模型、全盘内容扫描或大型搜索集群。 |
| 真实性 | 原始记录、规则推算、AI 摘要、缺失字段分别标识；未知不填零，推断不冒充实测。 |

### 文档结构

02–05：目标、架构、NAS 与部署；06–08：数据接入、设备身份与同步；09–10：统计口径；11–13：页面、会话与文件；14–15：交接与原生续聊；16–17：数据模型与 API；18–19：安全、性能和运维；20–22：范围、开发验收和风险；附录：资料依据与开发交接。

### 事实与假设的标记

“用户要求”来自本轮及上一轮需求；“建议默认”是本设计给出的可调整方案；“待核验”必须由开发 Agent 在真实机器验证。文档中的资源预算、性能门槛和阶段安排均为设计目标，不是已经完成的实测。

文档基线日期：2026-09-23。版本：PRD v0.1。状态：可用于开始数据验证和第一版开发，尚未在用户两台电脑及 NAS 上运行验证。

## 02  用户目标、范围与核心场景

单用户、双电脑、两个 Agent；优先解决“用了多少、做了什么、结果在哪”。

### 用户明确要求

整合 Windows 与 Mac 上的 Codex、Hermes；按设备、Agent、模型、日期查看单独或合并的耗时与用量。记录输入字符数、逐轮耗时、平均及累计时长、多会话并行情况、历史用量。按日期回看新旧会话，以三栏方式浏览标题、全文和关键事件，并关联文件位置及资源占用。

工作文档已有 NAS 存储位置。跨设备续聊属于可选增强：希望在 Windows 看到 Mac 做到哪里，利用已保存记录继续，而不依赖离开 Mac 前主动让 Agent 写交接文档。NAS 具体型号未确认，可能是约三年前购买的极空间 Z4S 或 Z4 Pro。

| 场景 | 应得到的结果 |
| --- | --- |
| S01 每日统计 | 选“今天 / 全部设备 / 全部 Agent”，查看总量，并能下钻到某台机器、某个会话、某一轮。 |
| S02 历史回溯 | 选 9 月 16 日，看到当天发生过交互的会话，即使会话并非当天创建。 |
| S03 多任务并行 | 同时开 3–4 个对话，区分累计执行时长与并行去重时长，并看到交错时间段。 |
| S04 下班后接着做 | Mac 停用后，在 Windows 读取最后已同步的对话和文件清单，确认缺失项后继续。 |
| S05 找回产物 | 从某轮对话找到文件，也能由文件路径查回生成或修改它的会话。 |
| S06 断网或离线 | 原 Agent 正常使用，采集器本地缓存；网络恢复后补传，不重算、不把旧数据算到今天。 |

### 首版不做

不替代 Agent 聊天界面；不做多用户团队平台、自动任务调度和远程任意命令执行；不同步账号密钥与 Agent 活数据库；不承诺迁移正在运行的进程、全部隐藏状态或历史 RAM 曲线；不默认复制所有 NAS 文件，不用 AI 补造缺失日志。

## 03  推荐架构与形式比较

“Web 应用”和“本机采集”并不矛盾：前者负责看，后者负责拿到数据。

```text
Windows：Codex / Hermes → 本机采集器 → 本地待上传队列
                                      │ HTTPS / API
Mac：    Codex / Hermes → 本机采集器 ──┤
                                      ▼
NAS Docker：接收与校验 → 中央数据库 / 搜索索引 → Web 页面
                                      │
                             交接快照 / 文件路径映射

两台电脑的浏览器均查看同一份 NAS 汇总结果。
```

| 方案 | 判断 |
| --- | --- |
| NAS Web + 双机采集器 | 推荐。页面统一，NAS 统一计算；本机负责读取本机可访问的数据。适合单用户双设备。 |
| 两套桌面端 + 同步数据库文件 | 不采用活数据库文件同步。易产生版本分叉、锁和冲突；改用 API 同步后，本质仍需中央服务。 |
| 只有 NAS 容器，不装采集器 | 不能直接看到两台电脑的本地日志、进程和未共享目录。可做手动导入，但不足以实现自动统计。 |
| 纯浏览器应用 | 可查看与手动导入；不能默认持续读取任意本地 Agent 数据和操作系统进程。浏览器文件访问有授权边界。[8] |

### 建议技术栈

前端：React + TypeScript；后端：Python + FastAPI；中心存储：SQLite + FTS5；采集器：Python，按 Windows、macOS 分别打包。选择理由是减少开发语言和基础服务数量，而不是追求大型平台架构。FastAPI 官方提供容器化部署指导。[9]

NAS 首版仅一个应用容器：后端同时提供编译后的静态前端；一个写入进程、短事务入库；搜索及统计先用数据库完成。暂不引入 Redis、Elasticsearch、Kafka、向量数据库或微服务。采集器先提供命令行诊断与登录自启动，托盘界面后置。

> 两台电脑不需要安装 Docker 来“看页面”；NAS 上的 Docker 也不会自动获得电脑的本地访问能力。

## 04  NAS 适配、硬件依据与负载预算

按较低配 Z4S 作为评估基线，但不根据购买年份猜定实际型号。

| 可能型号 | 官方规格摘要 | 本方案判断 |
| --- | --- | --- |
| Z4S 普通版 | Intel N5105，4 核 4 线程；4GB / 8GB DDR4 可选。[1] | 具备尝试部署轻量数据服务的硬件条件；4GB 版本需重点看剩余内存。 |
| Z4S 旗舰版 | Intel N6005，4 核 4 线程；8GB DDR4。[1] | 按本方案的数据服务职责，预计有更宽松的资源空间，仍需实测。 |
| Z4 Pro | N97；性能版 i3-N305；内存有 8GB / 16GB，性能版 16GB。[2] | 无需因本项目先购买或升级设备；确认当前配置与容器负载后再判断。 |

Z4S 官方页面列出了 Docker 相关能力。[1] 是否能直接使用 Compose、哪些卷路径可用、容器资源限制入口在哪里，仍取决于实机 ZOS 版本。文档不写死极空间内部系统路径。

### 工程预算，不是实测结论

| 项目 | 建议目标 / 策略 |
| --- | --- |
| NAS 应用内存 | 稳态目标 ≤512MB；初始容器上限可设 1GB，是否适合以 NAS 剩余内存为准。不能把限额当实际占用。 |
| CPU | 先限制最多使用约 1 个逻辑核；首次导入与建索引单任务、分批运行，在线新数据优先。 |
| 本机采集器 | 稳态内存目标 ≤150MB / 运行环境；不加载模型，不定时扫描全盘。 |
| 存储 | 初期建议预留 5–10GB 给记录、索引和滚动备份；这是预留空间，不是必然占用。 |
| 数据库位置 | NAS 本机持久化卷；已有 SSD 卷时优先放索引与数据库。机械盘可验证，但写入可能影响休眠。 |

负载主要来自历史日志导入、全文索引、频繁磁盘写入和大文件扫描，而不是图表数量。文档文件仍留在原 NAS 目录，只记录路径与必要元数据。浏览器承担界面渲染；模型调用仍由原 Agent 完成。

> 部署前读取“型号 / CPU / 总内存 / 可用内存 / 已有容器负载 / 可用磁盘”。若可用内存不足约 1GB，先调低批量与保留策略并测量，不据此直接承诺流畅，也不要求先升级硬件。

## 05  部署、网络访问与存储边界

中央数据库放在 NAS 本地卷，通过网络传记录，不通过网络共写数据库文件。

### 部署拓扑

NAS：一个 linux/amd64 应用镜像，一个持久化数据卷。Windows、Mac：各自安装采集器并登记设备；浏览器访问同一 Web 地址。若 Agent 实际运行在 WSL、虚拟机或远程主机，采集器应在其实际数据环境内读取，归入同一物理设备的不同运行环境。

中心数据库示例容器路径为 /app/data/workspace.db；这是本工具路径，不是现有 Agent 的数据库。NAS 主机侧目录由部署向导选择。原工作文件目录默认不挂载；需要查看 NAS 文件状态时，仅把明确授权的项目目录以只读方式挂载。

### 不采用的同步方式

不把活跃的 Codex / Hermes 数据目录重定向到 SMB；不让两台机器读写同一个 SQLite 文件；不使用同步盘软件复制正在写入的数据库来实现实时同步。SQLite 官方指出网络文件系统存在一致性与锁风险，WAL 也要求共享内存参与方处于同一主机。[5][6]

### 家里与办公室如何连通

局域网内可直接访问 NAS 服务。跨网络建议经可信 VPN / 组网链路访问，再叠加应用登录及设备令牌；首版不默认开公网端口。极空间客户端能远程浏览文件，不代表后台采集器已具备可稳定调用的 API 通路，必须单独验证电脑到本服务的 HTTPS 连通性。

不要求 NAS 主动连回办公电脑：两端采集器主动上报即可。公司网络不允许的连接不绕过；此时在允许的网络补传，或手工导入本工具的不可变导出包。

### 离线能力的真实边界

NAS 离线：Agent 仍能使用，采集器继续缓存，但中央 Web 页面可能打不开。Mac 休眠或关机：Windows 可以看已同步内容，不能取得尚未上传的尾部消息。本地离线浏览完整中央历史不列为 MVP 要求；以后可增加只读本地缓存。

> 若无法建立双机到 NAS 的长期连接，可降级为“每设备独立不可变 JSONL 包 + NAS 导入”。这不是同步活数据库，也不保证实时；主方案仍为 API 增量同步。

## 06  数据接入与能力探针

首先识别真实版本与数据结构，再决定哪些指标可以精确展示。

| 来源 | 优先接入 | 必须验证 |
| --- | --- | --- |
| Codex | 使用实机支持的只读会话接口，或读取已落盘的会话记录。官方 App Server 提供 thread/list、thread/read、轮次及用量事件。[3] | 版本、CODEX_HOME、桌面 / CLI / IDE 的实际存储；是否覆盖已有会话；事件是否来自现有实例。 |
| Hermes | 按实际 HERMES_HOME / Profile 解析 state.db，读取会话、消息和已有用量字段。官方文档记录了这些存储对象。[4] | 实际 schema_version、Profile、累积用量粒度；是否存在压缩存档、旧版 JSONL 或子 Agent 记录。 |
| 运行资源 | 在 Agent 所在环境采集进程级指标，并建立可验证的会话关联。 | 能否关联到独立进程；共享进程、子进程、WSL 和远程环境边界。 |
| 文件 | 先提取成功文件操作和明确的产出引用；补充受限目录的元数据检查。 | 相对路径、cwd、沙箱目录、临时文件、NAS 映射、是否确实已创建。 |

### 读取现有数据时的保护要求

只读访问原文件；不调用可能自动迁移数据库的 Agent 初始化代码。SQLite 使用短只读事务；需要快照时使用一致性备份接口，不直接复制热数据库的单个主文件，不把正在变化的数据库标成 immutable。不修改原 Agent 的认证、配置或运行策略。

不能假设“启动另一个 App Server”就订阅到了桌面端已有窗口。先验证读取会话与观察事件的覆盖范围，再决定是否补接官方事件；无法旁路观察的功能必须明确列为有限支持，不悄悄替换用户入口。

### 探针输出格式

每个来源生成 capabilities.json：Agent 版本、采集器版本、数据范围、会话及消息计数、可用时间字段、用量粒度、模型字段、文件事件、资源关联能力、历史缺失说明。示例能力状态为 supported / estimated / missing / incompatible。

> 记录“可获取的对话原文和工具过程”，不承诺恢复原平台未保存、已经删除、仅有压缩摘要或根本不对外提供的内部状态。历史缺口需要在时间线显示。

## 07  设备身份与跨平台归属

设备字段必须进入每次执行，而不是只写在会话创建记录上。

| 身份 / 维度 | 定义与用途 |
| --- | --- |
| physical_device_id | 用户命名的物理设备，例如 Mac-工作、Windows-家用。OS 是属性，不用 OS 名充当唯一 ID。 |
| environment_id | native、WSL、容器或远程执行环境；一台电脑可以有多个环境。 |
| source_instance_id | 某个 Agent 安装与 Profile 的稳定来源标识；防止不同 Profile 误合并。 |
| session_id / native_id | 本工具全局会话标识与原 Agent 标识分别保存；不可用标题当主键。 |
| task_id | 可选的跨会话任务关联。用于把 Mac 老会话和 Windows 新会话连起来，不抹掉各自历史。 |
| run_id / turn_id | 执行轮次。保存执行设备、输入设备、采集设备及其归属依据。 |
| origin / observer | 原始产生方与采集观察方分离；同一记录被两端看到，只计一次。 |

### 归属示例

Windows 浏览器查看 Mac 的历史：仍归 Mac。Windows 远程控制 Mac 上的 Codex：执行设备归 Mac，操作端可标 Windows。Mac 会话真正交接到 Windows 后：交接前的轮次归 Mac，后续轮次归 Windows。云端执行标为云端，不能冒充本机执行。

旧记录若只有采集机器信息，显示“来源设备：Mac；执行位置未核验”。跨设备复制过的日志不得直接认定为在目标机器执行。没有可靠证据时保留 unknown 桶，不以文件所在位置制造确定性。

### 同会话与同任务不是同一回事

原生迁移保留可验证线程身份时，可建立同一会话的多设备执行片段。通过交接上下文创建的新会话，必须保留新 native_id，并用 continuation_of / task_id 关联。标题相同、文字相似或目录一致，都不足以自动合并会话。

Hermes 若转调用 Codex，或父 Agent 汇总了子 Agent 用量，可能形成同一次执行的多层观测。需记录调用关系与计费覆盖范围。能用请求 ID 对齐就去重；无法对齐时显示“可能重复的未核验用量”，不把两个完整总数直接相加。

## 08  增量同步、去重与一致性

允许重复发送，但不允许重复计数；允许晚到，但不能改写发生日期。

### 同步链路

采集器增量读取 → 规范化与脱敏 → 本机持久化 outbox → 分批上传 → NAS 持久化确认 → 本机标记已确认。只有 NAS 确认持久保存后才能清理待上传项；统计与索引尚未更新时，页面分别显示“已接收”和“已索引”水位。

```text
事件信封示例（本工具设计，不是原 Agent 协议）
{
  "event_id": "stable-id", "schema_version": 1,
  "origin_instance_id": "mac-codex-default",
  "observer_device_id": "mac-work",
  "native_session_id": "...", "native_event_id": "...",
  "occurred_at": "2026-09-23T08:00:00Z",
  "sequence": 1024, "type": "turn.completed",
  "payload_hash": "...", "payload": {"status": "completed"}
}
```

| 问题 | 处理规则 |
| --- | --- |
| 重复与冲突 | 稳定事件键幂等入库。相同键相同内容直接确认；相同键不同内容隔离检查，不覆盖旧事实。 |
| 断网与重试 | 建议 10–30 秒批量上传，失败指数退避；本地保留待传状态。超过缓存上限告警，不静默丢数据。 |
| 日志截断 / 轮转 | 保存原生 ID、文件代际和游标；检测重建后重新核对，不仅靠文件修改时间扫描。 |
| 旧数据补传 | 按 occurred_at 回填历史；received_at 仅描述上传时间。重新计算受影响日期，不污染今日指标。 |
| 镜像与分叉 | 优先利用来源 ID、原生消息 ID、分叉祖先引用；不得只凭相同文本去重合法重复输入。 |
| 设备时钟偏差 | 保存 UTC、原始时区、序列及服务端接收时间；偏差提示，单轮优先用源端 duration / 单调时钟。 |

建议批次上限 200 条或约 1MiB，先达到者触发；大工具输出分块或保存为引用。具体参数可配置。重装采集器应重新登记并核对来源身份，不盲目重用另一台机器的设备 ID。

## 09  耗时、并行与活动片段口径

让图表回答正确的问题，而不是把“聊天开了多久”当成“Agent 干了多久”。

| 指标 | 定义 |
| --- | --- |
| 单轮响应耗时 | 结束时刻 − 开始时刻。优先使用原生接收 / 执行开始与终态；能测到提交时刻才叫“提交至完成”。注明起止依据。 |
| 累计执行时长 | 默认对顶层执行轮次求和，包含其内部工具与子任务等待；不再把已包含的子轮时长加一次。 |
| 并行去重时长 | 所选范围内所有执行区间并集长度。跨设备合并后重新求并集，不能直接相加各设备去重时长。 |
| 平均 / 中位数 / P95 | 默认仅统计时间字段完整的已完成顶层轮次；同时显示样本数和覆盖率。失败、取消单列。 |
| 会话跨度 | 第一条到最后一条活动的时间差，仅用于历史浏览；不当执行耗时。 |
| 活动片段 | 把一段集中交互聚合展示。建议空闲 30 分钟后新分段，可调整；不改变原始轮次和耗时。 |

### 并行示例

Mac 的任务 A 为 09:00–09:10，Windows 的任务 B 为 09:05–09:15。累计执行 = 20 分钟，合并去重 = 15 分钟。两台机器各自去重均为 10 分钟，但不能因此把全设备去重写成 20 分钟。两种时长都不是用户本人投入时间。

### 异常与不完整数据

收到开始、未收到结束：显示运行中；断联后显示状态待确认，不能无限增长为已确认工时。得到确定终态后再结算。历史仅有消息时间时，按明确规则推算并标记 estimated；无法界定终点的轮次不进入精确平均值。

等待审批、工具运行、排队等拆分，仅在有明确事件区间时提供；这些区间可能重叠，不把所有子项简单相加成总时长。模型响应耗时不等同模型“思考时间”。

### 跨午夜与筛选

执行时长按报告时区的自然日边界切分；平均值默认把整轮归到开始日，并在说明中注明。执行轮数分“当天新开始”和“当天有执行”两种，默认展示前者。报告时区首次读取浏览器设置并由用户确认，此后全局固定、可切换；不使用采集机器各自时区拼日表。

## 10  字符、用量、模型与费用口径

字符量、Token、Credits、费用和订阅余额分别记录，不互相冒充。

### 输入与轮次

输入字符按用户实际提交文本的 Unicode 码点计数，CRLF 归一为换行；包括空格和标点，不包括上传文件字节、系统提示和工具输出。Emoji 可能由多个码点组成，界面说明该口径。每次被接受的输入记一条；一轮中追加指令可增加输入条数，但不必增加执行轮数。

自动交接注入的历史和系统辅助上下文单列，不冒充“今天手写的字符”。历史记录无法区分时标注来源不完整；流式片段拼成最终消息后统计，不逐片段重复累加。

### 模型与计费字段

| 字段组 | 规则 |
| --- | --- |
| 模型身份 | 同时保留 requested_model、reported_model、provider、Agent、推理档位及速度档位；实测返回缺失时展示配置模型，标注依据。 |
| Token | 优先逐请求 / 逐轮；只存在会话累计量时保留累计，不伪造每日分布。缓存与推理量若已包含在 input / output，不能再次相加。 |
| 累计快照 | 按同一计数器代际求差；遇到重置或回退先判断 compaction / session reset，不把负数变成新增用量。 |
| 费用 | observed / estimated 分列；估算需保存价格版本、币种、有效日期与计费维度。无价格标未知，不能填零。 |
| Credits / 余额 | 订阅额度与 API 账单不同；仅在有可靠来源时展示，来源时间必须可见，不用 Token 线性推算剩余额度。[10] |

### 每日、历史与合并规则

有请求时间则按请求发生日归集；只有轮次时间则注明按轮次归集；只有整个会话累计值则进入“跨日未分配”。设备与 Agent 合并先去重实际消耗，再汇总。不同币种不直接相加；换算仅作为可选估算。

全局聚合必须显示覆盖率，例如“精确逐轮耗时覆盖 86%；有模型用量的轮次覆盖 92%”。父子 Agent、转调用和镜像日志的费用覆盖范围单独记录，避免同一笔消耗出现两遍。耗时对比只描述实际工作负载，不宣称是模型能力排行榜。

## 11  总览页面与设备合并设计

一个全局筛选器贯穿统计、时间线和明细，避免三处各算一套。

```text
总览    会话    设备与设置

日期：[今天 / 最近7天 / 自定义]   设备：[全部 / Mac / Windows]
Agent：[全部 / Codex / Hermes]   模型：[全部]   时区：[报告时区]

执行轮数 | 累计时长 | 并行去重时长 | 输入字符 | Token / 费用

设备对比：Mac-工作 / Windows-家用 / 未知或云端
并行时间轴：按设备与 Agent 分组，每条会话显示真实执行区间
用量趋势：每天的模型消耗，可切换 Agent、设备和模型维度
明细：会话 → 本次活动 → 轮次 → 原始事件
```

### 全设备和单设备

“全部设备”是同一套明细的汇总视图，不复制成第三份独立数据。选择 Mac 时所有卡片、趋势、活动列表同步过滤。多设备选择可同时看 Mac + Windows，并保留分组显示。显示未知来源，不能为让总数好看而隐藏。

设备对比列显示：执行轮数、累计时长、设备内去重时长、输入字符、Token、最后同步、数据覆盖率。总行的去重时长单独计算；不能把这一列直接 SUM。内存不与用量卡片混为“资源总量”。

### 可下钻与可复核

点累计时长打开构成它的轮次；点某日用量定位当天来源明细；点时间轴片段进入会话并定位该轮。筛选条件、日期、会话 ID 与定位锚点可写入 URL；刷新与浏览器返回不丢当前位置。

### 同步状态必须能看见

页头展示每设备最后已接收 / 已索引时间、在线状态及已知待传量。离线设备不能宣称“当前没有新数据”，应写“已同步至 18:03，之后状态未知”。时间线迟到补传后刷新相关日期。

### 视觉与交互

统一白色背景，浅灰分隔与单一低饱和强调色。默认少量核心卡片，细指标收进详情。图表不依赖颜色唯一表达；时间轴支持缩放、拖动和定位今天。Agent 图标与设备文字标签同时出现。窄窗口折叠右栏，不压缩成无法阅读的三列。

## 12  会话三栏、活动审计与搜索

按当天发生过的活动组织，而不是只按创建日期或最后更新时间排序。

| 区域 | 内容 | 关键行为 |
| --- | --- | --- |
| 左栏：日期与会话 | 日期选择、活动片段、会话标题、设备和 Agent、状态、片段起止 | 选一天显示当天有活动的会话；同一会话一天多段可折叠。 |
| 中栏：对话过程 | 用户输入、回复、工具过程、文件引用；定位到所选活动 | 长日志折叠、按轮次展开、跳到完整会话、复制单条或导出选定范围。 |
| 右栏：活动 / 资源 | 首次交互、再次继续、模型变化、完成 / 中断、文件变更；另有用量与资源页签 | 事件点击跳回原文；文件点击查看路径及归属证据；右栏可收起。 |

### Audit 的定位

这是用于个人回看和排查的“活动记录”，不是经过合规认证的不可篡改审计系统。每个节点保留来源引用、事件时间及数据依据。首次话题默认取首条用户输入预览；AI 概括必须标为摘要，并能回到原文。

“再次激活”首版定义为再次提交输入或继续执行，不声称记录所有打开页面行为。仅打开原 Agent 窗口并阅读而未发消息，日志未必可观察；本工具内的阅读历史可另行选择是否记录，不混入 Agent 执行时间。

### 搜索范围

首版支持标题、用户与助手文本、项目名和文件路径搜索；工具正文默认不进入全文索引，可按会话检索或后续启用。结果显示匹配片段、设备、Agent、日期及原文定位。后续可按状态、标签和任务关联筛选。

中文必须纳入测试。SQLite FTS5 的 trigram 查询对不足三个 Unicode 字符的子串存在限制。[7] 设计上对一至两个字查询使用有日期 / 会话范围的受限 LIKE 回退，设置结果上限与超时；不能直接把英文分词效果当作中文可用性。

### 长会话与异常状态

长会话按页加载，先渲染目标轮与邻近内容。压缩摘要、已归档内容、无法恢复的历史缺口分别显示。错误、取消、等待审批和断联状态以文字标识。隐藏 / 归档仅修改本工具的展示元数据，默认不删除源会话。

## 13  文件、目录映射与资源占用

“在哪个目录”不足以判断“由哪个会话产生”，文件关系必须有证据。

### 跨系统路径映射

为每个项目登记一个逻辑根目录，再配置各设备的路径。例如下列路径仅用于说明，部署时由用户选择。逻辑文件 ID 由 root_id + 相对路径生成，不把某台机器的绝对路径当成跨设备唯一身份。

```text
逻辑根：project-docs
Mac：    /Volumes/Work/Projects
Windows：Z:\Projects
NAS：    经授权的对应共享目录

相对路径：AgentDesk/spec/requirements.docx
逻辑定位：project-docs + AgentDesk/spec/requirements.docx
```

不能对所有路径一律转小写；需尊重大小写、Unicode 规范化、软链接与越界路径。记录原生路径、解析后路径、所在设备、检查时间和存在状态。未映射时仍保留原路径，提示目标机器不可直接访问。

### 文件关系与目录快照

区分明确创建、明确修改、读取引用、可能相关。成功文件操作优先；同目录扫描只能建立可能关系。一个文件改十次是一个文件、十次变更。记录路径、大小、修改时间、可选内容哈希、关联轮次和来源证据。只对授权项目生成有范围与截断标识的目录快照，排除 .git、node_modules、虚拟环境和构建缓存。

记录清单不等于同步文件内容。交接前检查目标路径可读、文件是否上传完成及版本是否改变。大文件不默认全量哈希；按需核验。代码项目优先各自本地工作副本与版本管理，避免为本工具强迫两端同时改同一 NAS 工作树。

### 磁盘、RAM 与上下文分开展示

磁盘：会话记录逻辑字节、明确关联文件当前大小、共享缓存分别显示；中央数据库体积不平均摊成“可回收空间”。同一 NAS 文件被多会话引用，汇总只算一次；各设备实际副本另计。

RAM：优先进程级驻留量和采样峰值。共享进程不硬分摊到会话；进程树按唯一进程去重，跨进程 RSS 也不等于严格去重的物理内存。上下文 Token 另列。历史未采集 RAM 不补造；源机器离线时只显示最后采样时间。

## 14  跨设备交接：推荐的通用路径

不用离开 Mac 前先生成一份交接文档，也不用把原会话强行复制进 Windows。

### 用户操作流程

Mac 正常使用 Agent，采集器持续上传可获取记录与文件变更。回家在 Windows 打开工作台，选择该会话并点击“在本机继续”。工作台展示同步截止点、最后一轮状态及文件可用性，用户确认后取得一个上下文包和启动提示。Windows 上的 Codex 或 Hermes 读取它、核对现状，再继续工作。

导出包由已保存记录直接组装，不必先调用模型写摘要。长历史需要总结时，可在 Windows 端的 Agent 读取原文后完成。首次实现采用“复制启动提示 + 本机可读文件”；不会假装已把消息自动注入另一个应用窗口。

| 交接内容 | 保存与使用原则 |
| --- | --- |
| 交接标识与截止点 | handoff_id、源会话 / 设备、事件水位、最后同步时间、生成时的终态或未完成状态。 |
| 对话原文 | 最近若干轮 + 完整可获取原文的分页或文件引用；保留用户、助手和工具角色。 |
| 进展与决定 | 有明确记录的目标、用户约束、最近回复、计划和测试结果；推断摘要单独标识，不捏造“已完成”。 |
| 文件清单 | 逻辑根、相对路径、目标设备路径、存在状态、最后检查时间、可选哈希 / Git 版本。 |
| 环境差异 | 系统、cwd、必要工具版本及配置说明；只传描述，不复制 API Key、登录令牌或私钥。 |
| 缺失与风险 | 未同步尾部、源端仍在运行、附件缺失、文件已变更、无法重现的临时环境。 |

### 建议导出结构

```text
handoffs/<handoff_id>/
  handoff.json       # 截止水位、来源、映射与缺失项
  recent.md          # 最近活动，可快速阅读
  transcript.jsonl   # 已保存的完整可获取对话
  files.json         # 文件清单、版本与本机路径
  start-prompt.txt   # 让目标 Agent 先核验再继续的提示
```

导出目录属于本工具，不修改源项目文件。长输出按需读取，避免每次把全部历史重塞给模型。新会话建立 continuation_of 与 task_id 关联，Windows 后续消耗归 Windows。Mac 历史账目不重复入账；Windows 模型重新读取历史产生的新 Token 消耗，仍应正常统计。[10]

## 15  续聊分层与官方能力边界

截至 2026-09-23，不能再笼统地认为跨设备只能手写交接文档。

| 层级 | 能力与适用条件 | 优先级 |
| --- | --- | --- |
| L0 跨机回看 | 两台机器都能查看已同步原文与文件清单；原机可以离线。 | MVP 必须 |
| L1 上下文接续 | 从已同步内容组装交接包，在另一台机器新建会话继续；不恢复原进程。 | 首个增强版 |
| L2 官方远程继续 | 在支持的客户端中连接另一台设备，使用远端现有聊天与环境；源主机须在线、醒着并满足版本与权限条件。[11] | 条件接入 |
| L3 官方主机交接 | 官方文档描述在连接主机之间交接聊天与 Git 状态；要求匹配的 Git 项目和目标主机，执行中交接会中断当前响应。[11] | 专项验证 |
| L4 任意热迁移 | 迁移运行进程、临时状态、工具环境及任意文件系统上下文。 | 不承诺、不自研 |

### 对用户场景的推荐

优先实现 L0 + L1，因为既覆盖 Codex，也覆盖 Hermes 和普通文档项目，而且 Mac 关机后仍能利用最后已同步内容。原生远程连接与 Handoff 能用就复用，不为它们重新开发一套远程控制系统。

官方 Remote 的桌面端控制入口有分批开放说明，文档中的能力不代表用户现有版本已经启用。[11] 官方 Git 主机交接不应直接外推为“任意 NAS 文档任务都能在 Windows 本机原样恢复”。

### 会话恢复不是系统状态搬迁

Codex 的 thread/resume 是继续可访问的已有线程接口，不等于自动同步两台电脑的数据和工作目录。[3] 不把整个 ~/.codex 或 Hermes state.db 复制到另一台机器作为默认方案；这会混入本机状态、Profile 和可能敏感的配置。

### 交接的保护措施

源端仍在执行时先告警；允许用户查看已完成部分，但不默认中止源端。两台机器同时从同一截止点继续时，形成分支并提示冲突，不按最后写入覆盖另一支。文件路径映射成功后还要核对版本；NAS 有文件名不等于有正确版本。

> “原会话继续”“远程仍在 Mac 执行”“Windows 新会话接着做”必须使用不同按钮文案。尤其远程操作不能误标成任务已转移到 Windows。

### 建模约束

所有事实型记录带来源、时间和质量字段；数值缺失用 NULL。原始事件与投影分离：晚到数据可以重建投影，但不篡改旧事实。消息修订保留版本；计费事实与展示快照不能共用一个可随意覆盖的累加字段。

身份关系按事件 / 轮次归属，不按会话创建设备一劳永逸归属。可缓存按日聚合，但缓存不是唯一事实来源。删除与隐私清理应同时处理全文索引和派生快照。

## 17  API、索引与本机联动

API 名称是本产品建议接口，不是 Codex 或 Hermes 的现成接口。

| 接口 | 用途 / 约束 |
| --- | --- |
| POST /v1/devices/pair | 一次性配对码换设备令牌；令牌仅获本设备写入权限，不获得远程执行权限。 |
| POST /v1/ingest/batches | 幂等接收事件；返回已持久化水位、接受 / 冲突 / 无效记录；限流与大小限制。 |
| GET /v1/health/sources | 各来源最后接收、索引、水位、版本、兼容性与缺口；需登录。 |
| GET /v1/stats | 按日期、设备、Agent、模型聚合；包含口径、质量与覆盖率。 |
| GET /v1/sessions | 按活动日期筛选和分页，标题 / Agent / 设备等过滤；区分创建日期。 |
| GET /v1/sessions/{id}/events | 按游标分页读取对话与关键事件，支持定位轮次。 |
| GET /v1/search | 中文 / 英文检索，返回原文锚点；短词查询设范围和超时。 |
| GET /v1/files/{id} | 返回映射路径、版本、存在状态和关联会话，不接受任意外部路径读取。 |
| POST /v1/handoffs | 基于已同步截止点生成结构化上下文包；默认不调用模型。 |
| GET /v1/handoffs/{id} | 仅授权用户 / 设备读取，导出链接可撤销；不使用公开永久分享链接。 |

### 浏览器与采集器的职责分离

Web 第一版提供“复制本机路径 / 导出交接包”。点击浏览器按钮直接打开本地文件夹，需额外本机助手协议或授权接口；没有助手时不假装可用。后续本机联动只能执行白名单动作，如打开已登记目录，不提供任意 shell。

### 查询性能与索引策略

会话按活动日期、设备、Agent 和时间建立索引；消息正文按需全文检索。页面使用服务端分页与虚拟列表。首版不保存每个流式 Token 片段为独立搜索文档，最终消息是主展示对象。超长工具输出按引用保存，避免撑大常用查询。

实时页面可采用短轮询；只有页面打开时刷新，建议 5–10 秒。采集上传频率与页面刷新频率分开。缺失数据返回明确状态和解释，不能让空数组看起来像“该日没有活动”。

## 18  安全、隐私与数据完整性

对话可能包含工作资料；“放在自己的 NAS”不等于可以省略权限和隔离。

### 采集前与传输时

用户明确选择 Agent 数据目录、Profile 与项目范围。支持全内容采集、仅统计、排除会话三种策略；完整跨机回看依赖相应内容已被允许上传。采集器普通用户权限运行，不扫描整个用户目录。凭据文件、私钥和环境密钥默认排除；正文中疑似密钥在上传前按规则脱敏，标记已脱敏，不宣称百分之百检测。

NAS 页面需登录；设备令牌独立、可撤销；不同权限区分只写采集与读历史。跨非可信网络使用 TLS；不能只因为用了 VPN 就取消应用认证。日志不得记录令牌、完整请求头或默认输出整个对话。

### 容器与文件权限

容器非特权运行，不挂载 Docker socket，不映射 NAS 根目录。数据库卷可写，授权工作目录只读；资源采集在客户端，不为统计给 NAS 容器宿主机 root。文件接口只接受逻辑文件 ID，经路径规范化和白名单校验后解析，防止 ../ 与软链接越界。

### 存储、保留与删除

NAS 数据目录应限制访问；磁盘加密能力以实机配置为准，不默认宣称数据库已加密。会话内容默认保留到用户主动清理，原始日志和资源高频采样使用可配置保留期。删除前说明会影响中央副本、索引、交接快照以及备份何时轮换失效。

默认不删除原 Agent 数据与 NAS 工作文件。源文件消失只记录状态；不能因本工具归档会话就同步删除项目文件。中央备份不等同工作文件备份，应分别说明覆盖范围。

### AI 摘要与交接安全

交接与搜索返回的历史内容属于待处理资料，不应被程序直接当成系统命令执行。自动摘要默认关闭；启用时明确数据会发送给哪个模型 / 供应商、预计消耗及允许范围。保存摘要版本与证据引用，不能用摘要替换对话原文。

> 不需要复制 Codex / Hermes 登录态才能完成统计和交接。任何“继续工作”动作仍受目标 Agent 原有权限、沙箱和用户审批控制。

## 19  性能、备份与可观测性

先给可测的预算，再用真实数据决定是否需要优化或换存储。

| 方面 | 建议验收目标 / 运维规则 |
| --- | --- |
| 测试基线 | 2 台设备，2 种 Agent，约 10,000 个会话 / 100,000 条消息；记录总字节和工具日志量。大文本不能只用条数描述。 |
| 页面响应 | 局域网、索引完成后，常用总览和会话列表 P95 ≤2 秒；常规全文查询 P95 ≤3 秒。短中文回退单独测量。 |
| 可见延迟 | 在线增量数据通常在 30 秒内进入页面为目标；历史回填不要求即时，并显示进度。 |
| 资源预算 | NAS 稳态 ≤512MB、本机采集器 ≤150MB 为目标；导入与索引峰值另测。Docker 可设置资源上限。[12] |
| 采样策略 | 建议进程采样每 30 秒一次，仅活动时高频；原始样本保留 7 天，再做分钟 / 小时聚合。资源模块可关闭。 |
| 错误可见性 | 解析失败、版本不兼容、队列积压、磁盘不足、时钟偏差、来源断联必须在状态页可见。 |

### 容量估算方法

每轮用户与助手文字若合计 8KB，一天 300 轮，纯文字约 2.4MB / 天、876MB / 年；这只是算例，未含工具输出、索引、WAL、交接副本和备份。真实预算应先抽样一周记录的字节分布，不把 Token 数直接当磁盘字节。

### 一致性备份与恢复

中心数据库使用 SQLite 一致性备份接口或受控快照流程；不要仅复制正在写入的 .db 文件。SQLite 官方提供在线备份 API。[13] 建议每日快照、滚动保留 7–14 份，并定期把一份备份复制到另一台设备；同 NAS 的备份不能覆盖 NAS 整机丢失。

升级前备份 schema 与数据，失败时回滚应用和匹配的数据快照；不让旧程序直接写新版 schema。至少完成一次真实恢复演练：恢复后总量、会话、消息和交接清单一致，采集器重传不产生重复。

### 性能下降的处理顺序

先减少流式碎片与全盘扫描，再限制导入并发、调整索引和历史保留，最后才评估更换数据库或硬件。不要在数据源尚未跑通时引入 PostgreSQL、向量检索或本地推理服务。

### 第一段代码应该是什么

不是完整前端，也不是账号平台，而是 read-only probe：列出来源、读取一条真实会话、输出标准化事件，并写一个去重和统计测试。随后立即让两台机器往同一个临时中心上传，验证设备归属，再做总览。

### 前期允许的不完整

允许部分旧会话没有精确耗时、个别工具文件事件缺失、续聊需复制提示、没有托盘 UI。不能接受用模拟数据冒充双机接通、重复计算 Token、按日志复制位置重分设备、长期破坏 Agent 性能，或为了漂亮图表虚构精度。

> 先在任意一台电脑开发中央服务，验证容器化后再迁到 NAS。迁移的是本工具的数据卷与服务，不是搬动用户现有 Agent 的工作目录。

不阻塞设计，但开发必须把未知项变成实机证据。

| 待核验项 | 本版默认处理 | 影响 |

### 主要风险与应对

R1 源格式升级：适配器记录版本与 fixture；不兼容停止该来源的增量投影并提示，不写坏原库。R2 数据重复：稳定事件键、祖先引用和用量覆盖范围；不能只看内容哈希。R3 文件过期：保存检查时间与版本，接续前重新核验。R4 存储增长：工具日志不全量索引，采样分级保留，批量写入。R5 误导性精度：指标带口径和覆盖率，估算单列。

### 本轮可以确定的产品决定

采用 NAS Web + 两端轻采集器；所有汇总支持设备 / Agent / 模型维度；以会话与活动片段为主线；文件保存逻辑路径映射；双机 MVP 优先；交接先做记录驱动的上下文包；RAM 与原生无缝迁移后置；不做活数据库文件同步。

> 这份 PRD 足以启动开发验证，但它不是已经跑通的兼容性报告。下一次有意义的反馈应是两端真实探针结果和一个端到端闭环，而不是更多脱离数据的概念页面。

## 附录 B  给开发 Agent 的执行说明

可直接作为开发任务入口。优先输出真实证据，再推进界面。

> 任务目标：完成“Mac / Windows 上的 Codex、Hermes记录 → NAS 中央索引 → 设备筛选、耗时用量、会话回看”的最小闭环。跨设备交接作为后续明确阶段，不先实现完整远程控制。

```text
deploy/          # Docker 构建、卷配置与备份说明
docs/            # 能力报告、验证报告、决策与限制
```

开发阶段遇到歧义，优先选择“只读、可回滚、可解释、最小闭环”的实现。每完成一个阶段报告真实完成项、未完成项和下一阶段阻塞；不把接口存在误当成用户环境已经支持。
