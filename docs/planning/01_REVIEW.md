# 原 PRD 审阅与决策记录

审阅对象：用户提供的《跨 Agent 工作台 产品需求与技术设计 PRD v0.1》，日期2026-09-23；参照同名聊天的两轮用户需求。

## 判断

原文已经是一份有价值、可启动验证和开发的PRD。推荐的产品形态、范围控制、统计真实性和数据边界均合理，不需要推倒重写。原文自己将状态写成“开发验证初稿”，并在§22声明不是已验证的兼容性报告，这一定位准确。

如果“完整可执行”指开发者知道先做什么、为什么做，原文已经达到；如果指开发者无需重新猜测账目、事件身份、错误恢复和版本范围，则还需要本次补充。尤其这些规则一旦由不同模块各自选择，成品即使页面齐全，统计也可能对不上。

## 原文已有且应保留的内容

- NAS单容器与两端轻采集器；只读访问原Agent；API同步，不同步活数据库。
- 累计与并行去重时长分开；顶层轮次不叠加已包含的子任务。
- 按真实执行环境归属；原始产生方和采集方分开；未知设备保留未知桶。
- Unicode码点、输入来源、缓存/推理Token子集、历史累计不能强分到每日。
- 30分钟活动分段、按发生过活动的日期回看、三栏与来源下钻。
- 中文短词搜索限制、路径大小写/Unicode/软链接、文件归属证据。
- 正文缺口、断网水位、只读SQLite与一致性备份、隐私及导出边界。
- 通用上下文交接优先、RAM和原生迁移后置；性能目标没有冒充实测。

以上不是本次新发现的遗漏。本次只补工程契约，不把已有正确原则重新包装成修复。

## 新冻结的主要决策

| 编号 | 决策 | 原因 |
| --- | --- | --- |
| D01 | 单用户NAS服务；React/TypeScript + Python/FastAPI + SQLite，一个服务写入者 | 保持原方案轻量，不引入新的基础设施依赖 |
| D02 | 默认报告时区Asia/Hong_Kong，可显式修改；始终按IANA自然日边界 | 与当前用户环境一致，避免两台设备各自分日 |
| D03 | V0.1不估造历史精确轮次；可以显示明确命名的估算区间，但不进精确主卡 | 历史消息间隔不足以证明实际执行 |
| D04 | 数值NULL、缺口、部分覆盖、未分配用量都是正式状态 | 避免为了好看自动填0 |
| D05 | 不读取现有Agent凭据；初期不自动安装Hooks | 旁路采集优先，Hooks仅在实机验证后显式启用 |
| D06 | 事件只追加，投影可重建；更正通过带来源的修订事实完成 | 保留可追溯性，解决晚到和解析器升级 |
| D07 | 传输采用至少一次发送，事实幂等；不宣称网络“恰好一次” | 重试和重启都能恢复 |
| D08 | 导出内容包不等于文件同步、进程迁移或自动开始开发 | 保持“在本机继续”的真实含义 |
| D09 | 账号额度、成本自动估价后置；已记录费用可作为只读字段呈现 | 主需求是时间与用量，无需价格服务阻塞MVP |
| D10 | 真实安装组合决定探针数量；双机、双Agent目标保留 | 不假设四种组合都安装，也不把缺主要来源的版本称完整MVP |

## 技术事实核查后的细化

原文关于 Codex App Server 覆盖的警告正确。补充规格进一步区分历史读取与现有桌面运行事件；不把 thread/read 当订阅。Hermes 的累计模型用量行也不等于逐请求明细，first_seen/last_seen不能用于伪造每天的历史用量。路径、Hooks覆盖和字段需按安装版本探针确定。官方资料与核查日期见 [06_SOURCES.md](06_SOURCES.md)。

## 开发前仍无法从文档替代的证据

NAS型号、可用内存、ZOS/容器权限、两台电脑实际运行入口、Hermes Profile、办公室网络和真实文件映射均保留为P0/部署期验证项。当前仅确认本机目录中可见Codex会话目录和状态库文件名；没有因此认定字段兼容，也没有采集私人原文去证明产品效果。

这不是要求再讨论一轮产品方向。后续开发模型应按已有决定推进，遇到实机差异就提交能力报告和具体变更记录；无法测试的外部环境单列待验收。
